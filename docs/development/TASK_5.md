## 범위·사전 검토

- 파일 저장소·`Note` 계약을 그대로 사용합니다. 검색 인덱스만 구현하며 작업 6 자동 저장과 WPF 검색 UI는 포함하지 않습니다.
- `SqliteNoteIndex(string databasePath)`는 검색 전용 SQLite 파일을 사용합니다. 사용자 메모 본문은 Markdown이 정본이며 검색 DB의 메타데이터는 파생 데이터입니다.
- 공개 계약: `UpsertAsync(Note,CancellationToken)`, `RemoveAsync(Guid,CancellationToken)`, `SearchAsync(string,int,CancellationToken)`, `RebuildAsync(IAsyncEnumerable<Note>,CancellationToken)`.
- 작업 6은 저장 성공 이후 Upsert를 호출하고 작업 7은 외부 변경 조정 뒤 이를 갱신합니다. 재생성 시 없어지는 검색 캐시에 창 상태·즐겨찾기 등 비파생 데이터를 넣지 않습니다.
- `editor-web/README.md`의 기존 사용자 변경은 보존하고 커밋에서 제외합니다.

## 검증 기록

- 시작 전 전체 테스트 62개 통과.
- `SqliteNoteIndexTests` 23개를 먼저 작성하고 미구현 상태에서 전부 실패하는 것을 확인했습니다.
- 토크나이저 비교는 실제 SQLite 3.53.3에서 수행했습니다. 3글자 이상 한글 부분 검색은 trigram, 1~2글자는 `instr` 보완으로 결정했습니다. 자세한 수치와 한계는 `docs/research/SQLITE_SEARCH.md`에 기록했습니다.
- 구현 후 인덱스 테스트 23개 통과. Windows 유니코드 경로 대소문자 충돌 테스트를 추가해 실패를 확인하고 invariant 대문자 경로 키로 보완했습니다.
- 최종 패키지 잠금 복원 성공, WPF 포함 빌드 성공(C# 경고·오류 0). 기존 Monaco 청크 크기 경고는 유지됩니다.
- 검토 전 전체 테스트 87개(Core 3, Storage 56, Bridge 28) 통과.
- 별도 검토에서 NUL 포함 리터럴 검색이 FTS5 파서 오류를 일으키는 결함 1건을 발견했습니다. 회귀 테스트 실패를 확인한 뒤 NUL 포함 검색어를 `instr` 분기로 보내도록 수정했습니다. 검토에서 추가 주요 문제는 발견되지 않았습니다.
- 최종 전체 테스트 88개(Core 3, Storage 57, Bridge 28) 통과. Storage에는 기존 31개, 새 인덱스 25개, 토크나이저 비교 1개가 포함됩니다. 테스트 DB와 Markdown 입력은 모두 일회용 파일 또는 메모리 DB를 사용했습니다.

## 구현 판단

- 판단: 앱 UI 상태와 검색 DB를 분리합니다. 검색은 파생 데이터여야 안전하게 재생성할 수 있으므로 전용 DB만 허용합니다. 향후 호출부가 별도 파일 경로를 전달해야 합니다.
- 판단: 검색은 리터럴 부분 문자열이며 FTS 연산자·SQL 문법을 노출하지 않습니다. 전문 검색어 문법과 형태소·초성 검색은 이번 단계에서 제공하지 않습니다.
- 판단: 손상 파일을 일반 검색에서 자동 삭제하지 않습니다. 명시적 재생성에서 임시 DB 완성 후 기존 파일을 백업·교체하며 실패나 취소 시 이전 인덱스를 유지합니다.
- 판단: 재생성은 단일 소유자 작업입니다. 다른 프로세스·인스턴스의 사용을 호출자가 배제해야 하며 SQLite 보조 파일이 있으면 교체를 거부합니다.
