# SQLite 검색 정책과 한글 토크나이저 검증

2026-11-01 Windows x64, .NET SDK 10.0.403, Microsoft.Data.Sqlite 10.0.14, 번들 SQLite 3.53.3에서 측정했습니다. [공식 NuGet 패키지](https://www.nuget.org/packages/Microsoft.Data.Sqlite/10.0.14)를 고정하고 전이 네이티브 의존성을 잠금 파일에 포함했습니다.

## 비교

일회용 메모리 DB에 `개발자회의록 <번호> 한글검색인덱스구현` 형태의 문서 1만 건을 입력했습니다. 동일한 문서 테이블, unicode61 FTS5, trigram FTS5를 한 트랜잭션으로 구축했습니다. 검색 시간은 예열 후 `count(*)` 20회 평균입니다.

| 검색어 | unicode61 일치/시간 | trigram 일치/시간 | instr 일치/시간 |
|---|---:|---:|---:|
| 개발자회의록 | 10000 / 0.355ms | 10000 / 1.469ms | 10000 / 0.441ms |
| 발자회 | 0 / 0.006ms | 10000 / 0.359ms | 10000 / 0.465ms |
| 인덱스 | 0 / 0.006ms | 10000 / 0.357ms | 10000 / 0.707ms |
| 회의 | 0 / 0.006ms | 0 / 0.003ms | 10000 / 0.463ms |
| 의 | 0 / 0.006ms | 0 / 0.003ms | 10000 / 0.499ms |

3개 테이블 구축에는 약 90.3ms가 걸렸습니다. 이는 짧고 반복적인 데이터의 메모리 DB 토크나이저 비교이며, 디스크 검색 인덱스 전체의 성능이나 실제 사용자 문서 지연을 보장하지 않습니다. 시간 자체는 테스트 통과 조건으로 사용하지 않습니다.

재현: `dotnet test tests/HunminNotes.Storage.Tests --filter FullyQualifiedName~SqliteTokenizerBenchmarkTests --logger "console;verbosity=detailed"`.

## 선택한 정책

- unicode61은 공백 없는 한글 단어 내부를 찾지 못합니다. trigram은 3글자 이상 부분 검색을 지원하지만 1~2글자는 일치하지 않습니다. [SQLite FTS5 공식 문서](https://www.sqlite.org/fts5.html#the_trigram_tokenizer)의 제약과 실제 결과가 일치합니다.
- NFC 정규화와 invariant 대문자 변환으로 검색용 문자열을 만들며, 원래 제목·본문·태그 메타데이터도 별도로 유지합니다.
- 검색어는 앞뒤 공백을 제거한 **리터럴 부분 문자열**입니다. AND/OR·따옴표·`*`·`%`·밑줄·SQL 문법을 연산자로 해석하지 않습니다. 빈 검색어는 결과를 반환하지 않습니다.
- 3개 이상의 유니코드 코드 포인트 검색어는 매개변수화한 인용 FTS5 phrase로 후보를 찾고 `instr`로 실제 부분 문자열 일치를 확인합니다.
- 1~2개 코드 포인트 검색어는 정규화된 제목·본문·태그 열의 `instr` 스캔으로 보완합니다. 짧은 검색어는 전체 행을 검사하므로 큰 저장소에서 느려질 수 있습니다. 형태소 검색·초성 검색·오타 교정은 제공하지 않습니다.
- NUL(U+0000)이 포함된 검색어는 FTS5 문자열 파서가 처리하지 못하므로 길이에 상관없이 `instr` 보완 검색을 사용합니다. 저장 가능한 리터럴 문자열을 예외 없이 검색하기 위한 처리입니다.
- 긴 검색어는 제목 우선 BM25, 수정 시각, ID 순으로 정렬합니다. 짧은 검색어는 수정 시각과 ID 순입니다. 결과 개수 제한은 양수만 허용합니다.

## 저장·재생성

- 스키마 v1은 `application_id`와 `user_version`, `notes`, `note_tags`, FTS5 테이블을 갖습니다. 메모 ID 및 대소문자 무시 경로 키는 고유합니다. FTS rowid는 notes rowid와 공유해 갱신·삭제 시 전체 FTS 스캔을 피합니다.
- 등록·갱신·삭제는 메타데이터와 FTS5를 같은 트랜잭션으로 변경합니다. 경로 충돌 시 전체 변경을 롤백합니다.
- 검색 전용 파일만 이 클래스에 전달합니다. 창 상태·즐겨찾기 등 재생성할 수 없는 앱 상태 DB와 공유하지 않습니다. 다른 DB의 식별자나 알 수 없는 스키마 버전은 거부합니다.
- 재생성은 같은 디렉터리의 임시 DB에 먼저 모든 파일 데이터를 인덱싱하고 연결을 닫은 뒤 교체합니다. 파일 열거 실패·중복 ID·취소 시 이전 DB를 유지합니다.
- 손상 DB는 일반 검색·갱신에서 자동 초기화하지 않습니다. 명시적 재생성 시 기존 파일을 `.corrupt-<고유값>`으로 백업한 뒤 교체합니다.
- 단일 인스턴스 내 작업은 직렬화합니다. 재생성 중 다른 인스턴스·프로세스의 접근은 호출자가 배제해야 하며, WAL/SHM/journal 보조 파일이 있으면 교체를 거부합니다. 검색은 실제로 저장한 Markdown 파일의 변경을 스스로 감시하지 않습니다.
- [Microsoft.Data.Sqlite의 비동기 API](https://learn.microsoft.com/dotnet/standard/data/sqlite/async)는 SQLite 자체의 비동기 파일 I/O를 제공하지 않습니다. UI 통합 시 장시간 인덱싱·검색은 UI 스레드에서 분리하고 취소를 전달해야 합니다. WPF 연결은 후속 단계입니다.
